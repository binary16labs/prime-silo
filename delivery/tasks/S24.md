# S24 — possible duplicates: the rules beyond identical bytes, for review

## Goal

S21 and S23 find files that are byte-for-byte identical. That is the only kind of duplicate safe to
act on. Much of what the owner thinks of as duplicates is not identical:
- the same folder copied to F: twice;
- a photo shot as RAW and JPEG;
- a JPEG exported again at another size;
- a song whose tags were edited;
- a zip of a folder that also exists unpacked;
- two versions of one document.

S24 finds these with type-specific rules and shows them in the Library tab (and to Benny through
the S22 skill) as **possible duplicates for the owner to review**, each labelled with the rule that
found it and how sure it is. It never acts and never feeds S7 on its own.

## Why (measured on F:, 2026-10-11, Everything index only)

Owner content on F: is mostly photos and video:
- 129,818 JPEGs (499 GB);
- **27,923 Nikon RAW files (NEF, 352 GB)**, plus 864 Fuji RAF, 131 Canon CR2 and 67 DNG;
- 4,104 PNGs;
- 2,856 MP4s (389 GB) and 138 MOVs (134 GB);
- 1,394 MP3/FLAC;
- 1,080 7z archives and 69 zips;
- no HEIC.

Camera RAW plus JPEG pairs and re-exported JPEGs are the likely bulk of the "same photo, different
file" cases. NEF, CR2 and DNG are TIFF-based, so their capture metadata can be read without a new
dependency.

## The confidence ladder (normative)

| Level | Rule | Can feed an action (S7)? |
| --- | --- | --- |
| identical | full fingerprint match (S21/S23) | yes, with the owner's signature |
| identical folder | every owner file in two folders matches by full fingerprint, same relative names | yes, with the owner's signature |
| same content, different tags | the image or audio data matches, only embedded metadata differs | no, review only |
| same shot | same camera and capture time (EXIF), different files: RAW + JPEG, or re-exports at other sizes | no, review only |
| contained archive | a zip whose members (name and size) exist unpacked on the drive | no, review only |
| versions | same name in the same relative place, different content | no, review only, and never called duplicates |

## Design

1. **Folders (exact, no extra reads).** S23's levels make this exact for free: two identical folders
   have every file paired with a twin of the same size, so every member already carries a full
   fingerprint. A folder fingerprint is the hash of its sorted (relative name, size, sha256) for
   owner-scope files. Two outputs:
   - identical folders;
   - **containment**: the share of a folder's owner bytes whose content also exists outside it.
     A unique-size file is, with certainty, not contained.
   This is the unit the owner decides by ("Backups/2019-old is 100% elsewhere on F:").
2. **Same shot.** A hand-written reader takes capture time (DateTimeOriginal plus sub-seconds),
   camera make, model and serial, and image dimensions from:
   - JPEG APP1 EXIF;
   - TIFF-based RAW (NEF, CR2, DNG);
   - the JPEG preview inside a RAF.

   It reads only each file's header (first 64 KB; more only if an offset points further), and only
   for owner-scope images. A group of files with the same camera and capture time is labelled:
   - "RAW + JPEG" (keep both is a normal choice);
   - "re-export" (same shot, different dimensions; the largest is marked as the likely original);
   - "copy" when the bytes are also identical (already level 1 of the ladder).

   Files with no EXIF are not grouped by this rule.
3. **Same content, different tags.** Only for pairs another rule already links (same shot with
   equal dimensions, or same name with different size), the content is fingerprinted without its
   metadata:
   - JPEG: from the start-of-scan marker to end-of-image, skipping APP segments;
   - MP3: excluding the ID3v2 header and ID3v1 tail;
   - FLAC: audio frames only.

   A match means the two differ only in tags. This rule stays bounded: it never runs across all
   files.
4. **Contained archives.** A zip's central directory (at the end of the file, a small read) gives
   member names and sizes. When most members exist as files of the same name and size elsewhere on
   the drive, the archive is "contained (likely)", showing how many members are matched. 7z and rar
   are not read (no dependency; see owner questions).
5. **Versions.** The same file name (case-insensitive) under the same last two parent folder names,
   with different size or fingerprint, is "versions". It is shown so the owner never mistakes it for
   a duplicate.
6. **Where it shows.** The Library tab gains a "Possible duplicates" section grouped by rule, with
   counts, bytes involved, top groups and a CSV per rule, worked out in S21's background worker.
   The S22 librarian skill gains `possibleDuplicates(rule)`. Private paths are counted, never named,
   exactly as elsewhere, and the hub's loopback and policy guards apply.
7. **Within one drive.** Groups are found within one catalogue. The same rules across drives and
   machines belong to the consolidation epic, using the same code.

   directories, real ID3 tags):

## Acceptance (BDD — every Scenario must map to an automated test)

```gherkin
Feature: possible duplicates, for review
  Scenario: a folder copied twice is found exactly, without reading anything new
    Given two folders holding the same files under the same names
    When possible duplicates are worked out
    Then they are an identical folder pair, and no file was read beyond S23's levels

  Scenario: RAW and JPEG of one shot are the same shot, not a duplicate
    Given a NEF and a JPG from the same camera at the same capture time
    When possible duplicates are worked out
    Then they are grouped as "RAW + JPEG", review only

  Scenario: a song with edited tags is the same content
    Given two MP3s whose audio is identical and whose ID3 tags differ
    When possible duplicates are worked out
    Then they are "same content, different tags", review only

  Scenario: two versions of a document are never called duplicates
    Given two files of the same name in the same relative place with different content
    When possible duplicates are worked out
    Then they are "versions"

  Scenario: nothing below "identical" can be acted on
    Given any group found by a review-only rule
    When it is offered to anything that moves or deletes files
    Then it is refused as review only
```

## Pre-registered criteria (real F:, verifier, reported either way)

- Reading EXIF from every owner-scope image on F: (about 163k JPEG and RAW files) takes ≤ 45 min
  and reads ≤ 64 KB per file on average.
- Folder fingerprints and containment for all of F: are worked out in the background worker in
  ≤ 5 min from the catalogue alone, with 0 file reads.
- The counts per rule are reported. The verifier spot-checks, by bytes and metadata only (never
  opening or naming the owner's pictures), that 20 sampled "same shot" groups share camera and
  capture time, and that 20 "versions" groups differ in content.

## Owner questions (answer when signing)

1. **Visual similarity** (a perceptual hash that finds resized or recompressed pictures without
   EXIF, such as screenshots and downloads) needs an image decoder: a new dependency such as
   `sharp`, a native module. Recommendation: not now. EXIF covers camera photos, which are most of
   F:. It can be its own contract later.
2. **Video** (duration, resolution, codec) needs `ffprobe`, which isn't installed. Recommendation:
   not now. Identical video copies are already found exactly; re-encodes can come later.
3. **7z archives** (1,080 on F:) need a reader dependency. Recommendation: not now; zips only.

## Out of scope

- Any action on a review-only group. S7 accepts only "identical" and "identical folder", with the
  owner's signature.
- Rules across drives and machines (the consolidation epic).
- Perceptual image hashing, video metadata, 7z/rar (owner questions above).

## Handoff

One gate run and one independent check by a non-author verifier, using fixtures for the rules and
the real F: for the cost criteria. The verifier never names the owner's files.
