# S27 — measure the budget as the work goes, instead of predicting it once

**Signed by the owner 2026-10-25 as written.** Band S, 300 lines.

## Goal

Three contracts in a row have overrun their declared budget by 30 to 40 per cent — S21 (600 to 800),
S22 (600 to 953), S26 (800 to 1,104). The band rule was written to stop that and did not, because a
declared ceiling does not fix a bad estimator: it converts the error into retroactive bookkeeping,
and the conversation still happens at the end, when splitting is pure paperwork.

The figure is already a command — it was run a dozen times by hand during S26. Make it a check an
author runs continuously, so a branch crossing its band says so while there is still work left to
split.

## Context pointers (never inline content)

- `architecture/SPEC-work-contracts.md`: the bands, and the counting convention pinned on 2026-10-23
- `server/coordination/work-schema/validate.mjs`: `BUDGET_BANDS`, `OVERSIZE_GRANTED`, the band check
- `delivery/board/LOG.md`, the S26 lines: the three holes found by counting the figure by hand —
  phantom churn from a formatter, generated output, and `delivery/board`

## What to build

1. **A budget reading, derived not guessed.** Given a contract id and a merge base, report the
   non-test added lines under the pinned convention, the band, and how much is left. One command,
   usable mid-flight by the author and at the end by a verifier, so both derive the same number
   from the same rule rather than from each other's claims.
2. **The exclusions live in code, not in prose.** The convention excludes the contract file and
   `tests/`; it must also exclude `delivery/board/` and anything the build scripts generate
   (`manual/SITEMAP.md`, `manual/USE-CASES.md`, `manual/sitemap.json`, `manual/usecases.coverage.json`).
   Each of those was found by hand, after the fact, in the three contracts above.
3. **A formatter pass before measuring.** 180 of S26's lines were a JSON round-trip reformatting a
   file nobody had edited. The reading should say when unformatted files are inflating it rather
   than let an author argue about a number the formatter would change.
4. **No new ceremony.** This adds a reading, not a gate that blocks. An author who crosses the band
   is told, and takes it to the owner; nothing is refused automatically, because the band is a
   trigger for a conversation and the existing w0 check already enforces band equals budget.

## TDD plan

A fixture repo tree with known diffs: a contract file, a test file, a board file, a generated manual
file and two source files. The reading must count only the source files, and must change when the
source changes and not when the excluded ones do. Then one test proving the reading agrees with the
figure a verifier derives by hand on a real branch.

## Acceptance

```gherkin
Feature: an author knows their budget before they finish
  Scenario: the reading counts what the convention says and nothing else
    Given a branch touching source, tests, the contract, the board and generated output
    When the budget is read
    Then only the source lines are counted
    And the excluded files are named in the reading, so the exclusion is visible

  Scenario: crossing the band is said while there is still work to do
    Given a contract whose band is 300 and whose branch has added 310 source lines
    When the budget is read
    Then it reports the overrun against the band
    And it does not refuse anything

  Scenario: an unformatted file is named rather than silently counted
    Given a branch holding a file the repo's formatter would rewrite
    When the budget is read
    Then it says the figure may be inflated and which file to format
```

## Out of scope

Changing the bands or the ceiling. Blocking a commit or a merge on the reading. Rewriting the three
contracts whose figures were derived by hand — their numbers stand as recorded.

## Handoff

Nothing for the owner. The reading is for whoever is writing the next contract.
