# S14 — the map carries which software each node runs

## Goal

The estate map answers **"which node runs which Prime-Silo version"** from the hub, which is the
question that started EP-S and the one the plan (§3) promised would stop needing a report script.
S3 pushes counts and hashes only, so the fold carries `listed_apps: 1073` as a number and nothing
else. S4's applications matrix has no data source, and its version-drift Scenario cannot be met.

**Human-signed** (owner, 2026-09-21): this widens what crosses the LAN from counts and hashes to the
NAMES of installed software. Not a new surface — it rides the same authenticated, LAN-gated push —
but a broader payload on it, and that is the owner's call, not an agent's.

## What may cross, and what may not

Per application, three fields and no more:

- `name` — as the source reports it, judged by the hub's quarantine rules like every other string
- `version` — free text; two sources disagreeing is a fact about the estate, not an error
- `source` — the collector that saw it: `registry`, `winget`, `appx`, `services`, `tasks`, `ports`

**Never** `location` or `publisher`. The install location is a file path, and a file path is the one
thing this transport exists to keep off the wire (S3's D1 and E1 were both exactly that). The
publisher adds nothing the name does not and is another free-text channel. S0 already stores both
locally; they stay local.

The list is bounded like every other array in the payload, and an over-long one is refused rather
than truncated — a truncated inventory that reports success is the silent-incompleteness shape the
owner's directive forbids.

## TDD plan

1. Red: an app row carrying `location`, `publisher`, or any field the allowlist does not name
   refuses the whole payload, as every other unknown field does.
2. Red: an app name matching the hub's quarantine rules refuses the payload — the node cannot name
   privately-installed software the hub has ruled out.
3. Red: more apps than the cap refuses the payload; it is never silently truncated.
4. Green: the fold exposes each machine's apps, and `machineView` reports them per source.
5. Green: `versionDrift(fold)` names each product two or more machines hold at different versions.

## Acceptance (BDD — every Scenario must map to an automated test)

```gherkin
Feature: the map says which software each node runs
  Scenario: a path cannot ride in on an application
    Given an app row carrying an install location
    When the payload is judged
    Then the whole push is refused, naming the field and not its value

  Scenario: the hub's rules apply to software names too
    Given a hub whose policy quarantines a product name
    When a node pushes a map listing it
    Then the push is refused and nothing is recorded

  Scenario: version drift is answerable from the hub alone
    Given t480 holding Prime-Silo 1.24.5 and optimus holding 1.24.4
    When the fold is read
    Then Prime-Silo is reported as drifted, naming both machines and both versions
```

## Out of scope

The panel that draws this (S4). Install locations and publishers, permanently. Acting on drift —
updating a node is S7's executor and a signed proposal, not a button here.

## Handoff

Verifier confirms no install location or publisher can reach the hub by any field name, pushes a
real map from t480 carrying its real ~1,073 apps, and reports the payload size — the whole point of
this transport is that it stays small, and a size that no longer looks like counts and hashes is a
finding.
