# S6 — storage policy and the centralisation planner

## Goal

A declarative `coordination/estate/storage-policy.yaml` says where each category belongs (e.g. models -> nas:models),
minimum device coverage, and what never leaves its machine. A pure planner diffs the folded map and integrity
results against the policy and raises proposals through the existing governance ledger, never executing. Each
proposal carries bytes, file count, and sole-copy warnings.

## Amendment — consolidating backup drives (owner directive 2026-09-21)

The first real use of this planner is the owner's: _"consolidate all my backups from various drives
into this main one"_, with **report only, I decide each** as the disposition for a confirmed
duplicate (owner decision 2026-09-21). This contract already raises proposals and never executes,
which is that model; what it did not carry is the merge itself.

**Backup sets are trees, not categories.** F: holds several machine-shaped trees from earlier
consolidations (`Dell Inspiron 6400`, `lenovo`, `Optimus`, `backups`, `backup-preuninstall-*`,
`_Serato_Backup`, `phone`), and more drives are to be merged into it. The policy therefore gains a
`backup_sets` declaration: a list of tree roots that are being merged into one home, with F: the
declared home for this estate. Within a merged set the same content appears under different paths,
so a proposal is about CONTENT, not about a path: it names the content hash, every path holding it,
the one path proposed to survive, and why that one.

**Which copy survives is a rule, not a preference.** The surviving path is chosen by a declared,
deterministic order (the policy states it — e.g. deepest declared home first, then earliest mtime,
then lowest path key as the final tie-break) so that the same map and policy always propose the same
survivor. A proposal whose survivor cannot be decided by that rule is raised as needing a decision,
never resolved by scan order.

**Nothing is proposed for removal that integrity has not proven redundant.** A proposal may only
name a copy for removal when S5 classified that content `duplicate` from a FULL hash and the
surviving copy is on a device swept in this sweep. `suspected` content, and any content whose other
copies live on a device S5 reported `stale`, may be proposed for COPYING to the home but never for
removal.

Three further Scenarios, all required:

```gherkin
  Scenario: a merged backup set proposes one survivor per content
    Given the same file under two backup-set trees with one full-hash duplicate classification
    When the planner runs
    Then one proposal names the content, both paths, the surviving path and the rule that chose it

  Scenario: a survivor chosen by rule, not by scan order
    Given the same set of copies presented in a different order
    When the planner runs
    Then the same path survives and the proposal id is unchanged

  Scenario: suspected content is never proposed for removal
    Given content S5 classified suspected from a partial hash
    When the planner runs
    Then no proposal names any of its copies for removal
```
