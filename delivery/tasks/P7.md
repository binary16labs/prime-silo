# P7 — the navigation instrument: an agentic manifest the stream can score

## Goal

Make `tool_selection_accuracy` a number this estate has actually measured, instead of a field that
has been `unavailable` in every bench report it appears in.

The consumer already exists and is already honest: `derive_metrics`
(`runtime/benny/sdlc/bench_executor.py`) computes `tool_selection_accuracy` from `node_progress`
events carrying `detail.tool`, judged against a frozen rubric's `expected_ops`, and computes
`tool_efficiency` from `min_steps`. Nothing on today's orchestrator produces those events, and no
rubric exists, so both metrics are `None` in `docs/bench/results/p4-report.json` and in both rung
reports. The P4 amendment (owner-signed 2026-08-05) recorded this as an **instrument gap, not a
report defect**, waived the navigation block for P4, and carried the gap here.

This contract supplies the missing three: a manifest whose nodes require a real choice of tool, the
orchestrator emission that records the choice made, and a rubric frozen before any result is seen.

## The trap this contract exists to avoid

An instrument that cannot be failed measures nothing. If every node in the manifest admits exactly
one possible tool, `tool_selection_accuracy` is 1.0 by construction and the number is worse than the
`unavailable` it replaces, because it looks like evidence. The manifest must offer each judged node
a real choice among plausible tools, and the gate must prove the instrument can register a wrong
answer — by scoring a subject that deliberately chooses wrongly and getting an accuracy below 1.0.

## TDD plan

1. Red: a rubric whose `expected_ops` name no node that the run actually emitted leaves
   `tool_selection_accuracy` `unmeasured` — never 1.0, never 0.0. (Judging nothing is not a perfect
   score, and it is not a failing one either.)
2. Red: a node that emitted no `detail.tool` is neither a hit nor silently dropped from the
   denominator; the gate fails a derivation that counts only the nodes that answered.
3. Red: a rubric edited after results were seen is refused by hash mismatch, as P4's gate refuses a
   report that hides a gap.
4. Red: a manifest in which every judged node has exactly one candidate tool fails the gate as a
   vacuous instrument.
5. Green: wire `orchestrator.py` to emit `node_progress` with `detail.tool` at the point the tool is
   chosen, and run the manifest for real.

## Acceptance (BDD — every Scenario must map to an automated test)

```gherkin
Feature: the navigation metric is measured, or honestly unmeasured
  Scenario: a real run scores a real choice
    Given the agentic manifest and a rubric frozen before the run
    When a subject runs it and metrics are derived
    Then tool_selection_accuracy is a number, derived from node_progress detail.tool

  Scenario: the instrument can register a wrong answer
    Given a subject that chooses a tool the rubric does not expect
    When metrics are derived
    Then tool_selection_accuracy is below 1.0 and names how many nodes were judged

  Scenario: nothing judged is unmeasured, not perfect
    Given a rubric whose expected_ops match no node of the run
    When metrics are derived
    Then tool_selection_accuracy is unmeasured and the report says why
```
