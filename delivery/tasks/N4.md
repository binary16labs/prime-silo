# N4 — drift-delta engine (`estate_drift.mjs`)

## Goal

Compute the **actionable delta** between a satellite and the hub: the sessions (and executions) the satellite
holds whose content the hub corpus lacks — the true content-hash delta with the overlap excluded, so the
cockpit and the planner can show _what a sync would actually bring_. Pure functions over injected inputs
(reuses N0 CAS content-hashes + N1 `sessionStats`), no fs/net/hw, so it is deterministic and gate-testable.
Moves KR2.4 from "observe" toward "govern" by producing the signal a governed sync acts on.

## Acceptance (BDD — every Scenario must map to an automated test)

```gherkin
Feature: cross-machine drift delta
  Scenario: actionable delta excludes overlap
    Given hub content-hashes {h1,h2} and a satellite with sessions hashing to {h2,h3,h4}
    When driftDelta(hub, satellite, quarantine) runs
    Then clean = the sids hashing to {h3,h4} and h2 is excluded as already-present

  Scenario: quarantined sessions are counted, never surfaced
    Given a satellite session whose sid is in the quarantine set
    When driftDelta runs
    Then that sid is added to quarantined.count and never appears in clean (no sid/project/content emitted)

  Scenario: execution drift by content-hash
    Given hub L5 register hashes and a satellite register with one extra entry
    When executionDrift(hub, satellite) runs
    Then only the extra entry is returned
```
