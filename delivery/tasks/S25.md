# S25 — the librarian's edges: bound the work, and say what the answer means

## Goal

Three verifications of S22 ended with findings its verifiers judged non-blocking but real, and they
were left open when the owner merged. This contract closes them. It adds no capability: it bounds
work that is currently unbounded and documents answers that currently mean two things.

## Context pointers (never inline content)

- `delivery/board/LOG.md`, the S22 lines: the full findings list from `claude-s22-verifier`,
  `-verifier-2` and `-verifier-3`
- `server/coordination/lib/library.mjs`: `checkPaths` (the walk, the cap, `total`), `findFiles`
- `server/coordination/lib/estate_api.mjs`: the three query routes behind one shaper
- `delivery/tasks/S21.md` design point on the summary worker: the precedent for not doing
  unbounded work on the hub's request thread

## What to close

1. **Unbounded hashing on the hub's thread.** `checkPaths` hashes up to 500 files of any size, and
   nothing caps how many `paths` a caller may give — verifier-3 measured 20,000 paths costing 2.7 s
   of hub thread. S21 moved its 94-second summary to a worker for exactly this reason. Bound the
   request: cap the paths accepted and say so in the answer, as the walk cap already does.
2. **Two meanings of `total`.** `check`'s `total` counts files named; `find`'s counts matches before
   the limit. One feature, two meanings, neither documented.
3. **`find` with an empty `q` enumerates the drive** (rule-filtered). An enumeration surface nobody
   chose: either require a query or say in the docs that this is deliberate.
4. **A `check` of a folder the policy itself quarantines** answers a bare `total: 0` with no
   sentence — the owner asking about their own folder is told nothing, and not told why.
5. **The docs name no status codes.** `estate-library.md` documents neither the 404, the 202, nor
   `check`'s `total`/`withheld`/`capped`.
6. **A refusal writes no audit event**, which design point 10 of S22 arguably requires; and a client
   that aborts mid-check is audited as answered.

## TDD plan

Each item gets a test that fails first. For 1, a test giving more paths than the cap asserts the
answer is bounded and says it was. For 2 and 5, a docs test in the S21/S22 style reads the shapes out
of the source. For 3 and 4, the answer carries a reason. For 6, count events around a refusal.

## Acceptance

```gherkin
Feature: the librarian's answers are bounded and say what they mean
  Scenario: a caller cannot hand the hub unbounded work
    Given a check is asked about more paths than the cap allows
    When the hub answers
    Then it answers within the cap and says it was capped
    And the hub serves other requests throughout

  Scenario: asking about a folder the rules cover is explained, not blank
    Given a folder every file of which is quarantined
    When the agent checks it
    Then the answer says the rules covered everything it was asked about

  Scenario: the docs name every shape an answer can take
    Given the library routes as the API serves them
    When the documentation is checked against them
    Then every status and every field of an answer is named
```

## Out of scope

The contract defects three verifiers raised against S22's own text — no Scenario for the asked-about
side of `check`, none for duplicate paging, nothing on what a surface does when it refuses. Those are
scope and belong to the owner, not to this contract.

## Handoff

Nothing for the owner to do. The MVP journey does not wait on this.
