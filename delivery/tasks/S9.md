# S9 — the map model never reports what it did not store

## Goal

A sweep's published numbers describe only what was actually written: a collector that failed contributes no
counts, no totals and no snapshot rows. Added 2026-09-20 by owner decision after claude-s1-verifier-4 found
`runSweep` publishing the rows an errored collector had yielded before failing — with S1's walker, an
incomplete C: walk would publish ~2.2M phantom files while the index correctly held the previous listing.
This closes that, and the S0 hardening backlog recorded at S0's PASS, before S2 and S3 build on these numbers
(KR2.2: the physical estate joins the one event stream — with numbers that can be trusted).

## TDD plan

1. A collector that yields rows and then throws: `counts`, `totals` and the published snapshot contain none of
   its rows, for every kind (files, apps, media), and the volume keeps its previous listing. (N1)
2. Rows already written by that collector in this sweep are rolled back, not left for the next sweep to find.
3. `path_key` (the lowercased path) is judged by the quarantine rules like every other stored spelling: the
   İ / ẞ gap found at S0 PASS no longer lists a file whose key a rule matches. (backlog 1)
4. Configuration refusals clean the index first for the faults that currently throw early: non-array `scope`,
   `publicRoots` or `quarantine`, and a null collector. (backlog 2)
5. The snapshot contains only this sweep's file rows. (backlog 4)
6. Test-only gaps from S0's verifier, each as a test against today's behaviour: a policy fingerprint that
   ignores RegExp flags, an app's canonical location, trailing-separator spellings for app locations, and a
   drive-letter root for "..". (backlog 3)

## Acceptance (BDD — every Scenario must map to an automated test)

```gherkin
Feature: published numbers describe only what was stored
  Scenario: a collector that fails mid-listing contributes nothing
    Given a collector that yields rows and then throws
    When the sweep runs
    Then its rows are in no count, total or snapshot, and the volume keeps its previous listing

  Scenario: the stored key is judged like every other spelling
    Given a quarantine rule that matches only the lowercased path of a listed file
    When the sweep publishes
    Then that file is not listed and its key is nowhere in the index

  Scenario: a refused configuration still leaves a clean index
    Given a sweep called with a non-array scope and a rule that hides a listed file
    When the call is refused
    Then the index no longer holds that file

  Scenario: the snapshot is this sweep only
    Given a volume whose earlier sweep listed files that are gone now
    When a later sweep publishes
    Then the snapshot holds only the rows of the later sweep
```
