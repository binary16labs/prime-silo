# N5 — approve-to-sync governance (`estate_govern.mjs` + API + console)

## Goal

Make a satellite→hub sync a **governed, human-approved action**, not an ambient copy. The N4 drift delta
becomes a signed **proposal** carrying a privacy attestation (quarantined sids excluded before the owner sees
it); only an owner-approved proposal stages the clean delta into the hub via N0 `syncSource` (idempotent,
delta-only, KEL-logged) and emits an approval event on the B1 bus. Nothing moves on load — approval is the
trigger. This is the human-signed-stop that turns KR2.4 governance from a view into an action.

## TDD plan

1. Failing test: `proposeSync(delta)` excludes every quarantined sid and sets a privacy attestation flag → implement.
2. Failing test: `applySync` with `approved:false` (or missing signature) performs NO sync (syncSource not called).
3. Failing test: `applySync` of an approved proposal calls syncSource with exactly the clean sids and emits one bus event.
4. Failing test: re-applying the same approved proposal is a no-op (idempotence — syncSource's CAS/L4 dedup).
5. Failing test (mutation/RED): a proposal that includes a quarantined sid is rejected by `proposeSync`/gate.

## Acceptance (BDD — every Scenario must map to an automated test)

```gherkin
Feature: governed approve-to-sync
  Scenario: no sync without an owner signature
    Given an unapproved sync proposal
    When applySync(proposal) is called
    Then syncSource is never invoked and no approval event is emitted

  Scenario: approved sync stages only the clean delta, idempotently
    Given an owner-approved proposal with clean sids [s1,s2]
    When applySync runs and then runs again
    Then the first run stages s1,s2 via syncSource and emits one approval event, and the second run is a no-op

  Scenario: a quarantined sid can never enter a proposal
    Given a drift delta whose quarantined set contains sid q
    When proposeSync builds the proposal
    Then q is absent from the proposal and the privacy attestation asserts exclusion (gate RED if q leaks)

  Scenario: additive route, default unchanged
    Given the existing estate API
    When POST /api/estate/sync/propose and /api/estate/sync/apply are added
    Then GET /api/estate and every prior route respond exactly as before
```

## Out of scope

No live network discovery (N7). No auto-approval — the signature is the owner's. No new storage layer (sync
goes through N0 syncSource). No planner projection (N6). Do not weaken `personal_terms.json` or the quarantine.
