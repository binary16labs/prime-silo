# S2 — applications, services, scheduled tasks and ports

## Goal

Each node reports the software it runs: installed applications from the registry (HKLM, HKCU, WOW6432Node),
winget and Appx, reconciled into one list with versions; Windows services; scheduled tasks; listening ports with
owning process and bind address. "Which node runs which Prime-Silo / LM Studio / Tailscale version" is then read
from the map, not from a report script.

## Context pointers (never inline content)

- `architecture/SOLUTION-estate-map.md` §3 (apps table), §7 (ten-app completeness sample)
- `server/coordination/lib/heartbeat.mjs` (loopback-only services: observe locally, never probe remotely)
- S0 collector interface

## TDD plan

1. Parse fixtures of `reg query` Uninstall output, `winget list` and `Get-AppxPackage` JSON.
2. Reconcile: one product from registry and winget is one row listing both sources; conflicting versions are
   kept side by side, never merged.
3. Services, tasks and ports parsers; a port row names owning process and bind address.
4. A failing source (winget absent) yields a collector warning, not an empty application list.

## Acceptance (BDD — every Scenario must map to an automated test)

```gherkin
Feature: application inventory
  Scenario: one product reported by two sources is one app
    Given Prime-Silo in the registry at 1.24.5 and in winget at 1.24.5
    When apps are reconciled
    Then one row exists with sources registry and winget

  Scenario: a missing source is a warning, not an empty estate
    Given winget is not installed
    When the apps collector runs
    Then registry apps are present and the sweep carries a winget-unavailable warning

  Scenario: loopback services are recorded as loopback
    Given Benny listening on 127.0.0.1:8005
    When ports are collected
    Then the row binds 127.0.0.1 and is not reported as exposed
```

## Out of scope

Installing, updating or removing software; Linux/HAOS apps.
