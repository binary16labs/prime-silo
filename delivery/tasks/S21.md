# S21 — the librarian: a catalogue of F: that every question is asked of

## Goal

The owner opens the Estate Map, presses **Catalogue F:**, and the hub reads every file on F: once,
in folder order, into a local catalogue: path, size, mtime, full sha256, kind. After that,
"what is duplicated on F:" and "what on this backup drive is not on F:" are catalogue queries, and F:
is never re-read to answer them. Report only: nothing is moved or deleted. This is the owner's
2026-10-03 directive: "first thing is to be a librarian of the files and the store", before anything
more is added to F:. Making Benny manage the catalogue comes after this (see Out of scope).

## Why (measured, not assumed)

- S20's first real run on 2026-10-03 did 1,000 of 2,265,531 files in 30 min. It hashed F:'s
  same-size files as it compared, so the USB HDD seeked constantly (~77 reads/s, 300 KB/s). 94% of
  C: files share a size with some F: file, so the size test filters almost nothing.
- Measured on F: (1,500 small files each way): scattered order 26 files/s, sorted 28,
  **contiguous folder-order walk 85**. The catalogue reads in walk order, and only once.
- `nas_catalog.mjs` already does most of this (SQLite row per file, reconcile by
  add/change/move/remove, incremental by size+mtime). But it covers only `F:\nas`, which is
  empty (890 scans, 0 files). It holds the whole scan in memory and commits once at the end, so a
  multi-hour first pass that dies or is stopped loses everything.

## Design (the author may refine it; the Scenarios are normative)

1. **One catalogue per drive, keyed by drive identity** (volume serial + root file ID, the S20
   rule). It is stored under the estate store (`<ESTATE_STORE>/library/<identity>.db`). When the
   store lives on the drive being catalogued, the store folder is skipped.
2. **Walk order, batched, resumable.** Walk folder by folder and hash in the order walked. Commit
   every N files (author picks N; at most ~1 min of work is lost). A row whose path, size and mtime
   are already in the catalogue is not re-read. A stopped or crashed pass therefore resumes where it
   committed, and later passes only hash what changed. A pass that finishes reconciles removals.
   An unfinished pass never removes a row.
3. **Kind** comes from the extension (documents, images, video, audio, archives, code, models,
   other). It sits beside the existing top-folder `category`, which `F:\nas` keeps.
4. **Single flight and a Stop.** One catalogue pass per hub. A Stop button aborts at the next file
   boundary, keeps what was committed, and reports "stopped at N of M". Comparison runs also get a
   Stop (there was none, and on 10-03 the hub had to be restarted to cancel).
5. **Duplicates are a query.** Group by sha256 with count > 1. Show wasted bytes ((copies - 1) x
   size), the largest first, and the folders the copies sit in. CSV download.
6. **S20 asks the catalogue.** Comparing a drive with F: reads the DRIVE only. A drive file whose
   size is in no F: catalogue row is "only on the drive" without being read. Otherwise its full
   sha256 is looked up. A hash match is "on F:" only if the F: path still stats at the catalogued
   size and mtime (a metadata read, no seek into file data). If not, it is "changed since
   catalogued", which counts as unconfirmed and never as "on F:". The result names the
   catalogue's completion time. The partial-hash path stays for a target that has no catalogue.
7. **The existing `F:\nas` scan is unchanged.** It keeps its scheduled task, its KEL per-file
   artifact events and its tests. `scanNas` behaviour does not change.

## TDD plan

1. `library_test`: catalogue a temp tree; rows match the files (path, size, mtime, sha256, kind).
2. Stop after K files, then start again: the hasher is called only for the files not committed, and
   the final catalogue equals an uninterrupted run's.
3. Rescan with one file changed, one moved, one deleted: only the changed file is re-hashed. The
   deletion is removed only by a pass that finished.
4. The store folder inside the catalogued root is never a row.
5. Duplicates: two identical files in different folders give one set with wasted = size. Opening
   the catalogue's root for reading during the query fails the test (fs spy).
6. `estate_compare_test`: with a catalogue present, F: file data is never opened (hasher spy on the
   target side); size-miss gives "only on the drive"; hash match plus same stat gives "on F:"; hash
   match with a changed mtime gives "changed since catalogued". A catalogue that has never
   finished is refused with a reason.
7. Privacy: a quarantined path is counted in every total and absent from the duplicate list, both
   CSVs, every API response and the progress line.
8. `estate_map_panel_test`: Library tab shows Catalogue F:, progress (files, bytes, rate, ETA),
   Stop, totals by kind, duplicate sets. Backups tab shows "against the catalogue of <time>".
9. Gate `s21.mjs` runs `library_test`, `estate_compare_test`, `estate_map_panel_test` **and**
   `nas_catalog_test` + `nas_itinerary_test` (the regression on point 7 of the design).

## Acceptance (BDD — every Scenario must map to an automated test)

```gherkin
Feature: the librarian catalogue of F:
  Scenario: a stopped catalogue resumes without re-reading
    Given a catalogue pass stopped after some files were committed
    When the pass is started again
    Then only the files not yet committed are read
    And the finished catalogue equals one from an uninterrupted pass

  Scenario: an unfinished pass never forgets a file
    Given a catalogued file that the current pass has not reached yet
    When the pass is stopped
    Then the file's row is still in the catalogue

  Scenario: duplicates come from the catalogue, not the disk
    Given F: catalogued, holding the same bytes in two folders
    When the owner opens the duplicates
    Then one set of two copies is shown with the wasted bytes
    And no file on F: is opened

  Scenario: a backup drive is compared without reading F:
    Given F: catalogued and a drive holding one file F: has and one it does not
    When the drive is compared with F:
    Then the first is "on F:" and the second is "only on the drive"
    And no file on F: is opened for its data

  Scenario: a file changed on F: since cataloguing is not a copy
    Given a drive file whose hash matches a catalogue row whose F: file has since changed
    When the drive is compared with F:
    Then it is "changed since catalogued", never "on F:"

  Scenario: a private file is counted, not listed
    Given a quarantined path that is duplicated on F:
    When the catalogue and duplicates are shown
    Then it is in the totals and absent from every list, CSV and API response
```

## Pre-registered criteria (measured on the real F: by the verifier, reported either way)

- First full pass throughput ≥ 70 files/s over the small-file stretch (walk-order baseline 85,
  scattered 26). If it is below that, the report attributes the time (walk vs hash vs SQLite).
- File count within 1% of Everything's count for F: (minus the skipped store folder).
- A rescan of unchanged F: re-hashes 0 files. Its wall time is recorded (no target; it sets S22's
  scheduling decision).
- One real backup drive compared against the catalogue: F: data reads = 0 (process I/O counter on
  F:, or a hasher spy in the real run).

## Owner questions (answer before signing)

1. **Event history for the first pass.** `F:\nas` writes one KEL artifact event per file. For about
   1.1M files on F:, that is a log of hundreds of MB written in one night. Recommendation: the
   first pass records one summary event per committed batch (counts plus a running digest of the
   rows). Per-file events start only for changes after the first finished pass.
2. **Where the catalogue lives.** Recommendation: `F:\estate-store\library\` (it travels with the
   drive it describes, and the store folder is skipped). Alternative: `BENNY_HOME` on C:. That keeps
   F: read-only during the pass, but the catalogue is lost if the T480 is rebuilt.
3. **Full sha256 of every file.** About 1.4 TB at USB-HDD speed is roughly 4–8 hours for the first
   pass. Is an overnight first run from the panel acceptable? (Later passes hash only what changed.)

## Out of scope

- Moving, deleting or de-duplicating anything (S7).
- Benny's tools over the catalogue: find, duplicates and "is this on F:" via MCP (proposed S22).
- Scheduling library rescans; the Everything 1.5 journal for incremental passes (S22 once rescan
  time is measured).
- Other machines' drives; cataloguing C:.

## Handoff

One gate run plus one independent check by a non-author verifier on real files. A small real tree
is catalogued, stopped, resumed and compared against a real drive, and the four pre-registered
criteria are measured on the real F: and reported, whether they pass or fail.
