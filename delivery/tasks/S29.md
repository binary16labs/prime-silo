# S29 — a catalogue it cannot read is an answer, not an exit

## Goal

A locked or corrupt catalogue makes **every** library surface throw, and nothing catches it at the
route: the request is never answered, the client times out waiting for headers, and where the API
is embedded bare that is process exit. `claude-s26-verifier` constructed it with a second
connection holding `PRAGMA locking_mode = EXCLUSIVE` and an open write transaction, and measured
all eight:

```
folderView('')  folderView('keep')  duplicateNeighbours      — S26
findFiles       duplicateSets       checkPaths               — S22
catalogueLookup libraryState                                 — S21
```

Eight surfaces, eight throws, one message. It is a property of `readOnly()` and of there being no
catch at the librarian/route boundary, so no single contract's surfaces are at fault and fixing it
inside one would put that contract in charge of a boundary six others share.

**It is reachable in ordinary use, not only under corruption.** The worker holds the catalogue
read-write for a 157-second rollup on the real F:, and its closing `BEGIN / DELETE / ~25,600
inserts / COMMIT` is exactly the window. This estate lives in OneDrive, where sync and antivirus
take file locks. `BUSY_MS` is a two-second cap, not a guarantee — and that constant exists in this
file because a read meeting the worker's open once made the hub answer **500**. It no longer
answers 500. It does not answer.

## What to build

1. **Answer at the boundary.** One catch where the librarian meets the route, giving a distinct
   status and the reason — _the catalogue could not be read_, not _try again in a minute_. A lock
   may clear; a malformed file will not, and telling the owner to wait for something that will
   never arrive is worse than the throw.
2. **Do not widen a narrow catch to get there.** `rollupRows` turns only `no such table` and
   `no such index` into `computing`, deliberately. This contract adds a second, different answer;
   it does not relax the first. Swallowing every failure as progress is how the 45-minute freeze
   and the dead worker both stayed invisible.
3. **All eight surfaces, by test.** The verifier's lock recipe is deterministic — one test puts
   every surface under it and asserts each answers rather than throws.
4. **Say so in the docs.** `estate-library.md` names no status for an unreadable catalogue.

## TDD plan

A second connection taking an exclusive lock, then each surface in turn: all throw today, all must
answer. Then the two unreadable shapes — a smashed schema page (`database disk image is malformed`)
and a non-database file (`file is not a database`) — which must be distinguishable from a lock,
because one clears and the other does not. A paired positive on an ordinary catalogue, so the
answers are not being produced by everything being broken.

## Acceptance

```gherkin
Feature: an unreadable catalogue is reported, never fatal
  Scenario: a locked catalogue answers with its reason
    Given the worker holds the catalogue while it writes the rollup
    When any library surface is asked a question
    Then the request is answered with the reason it could not be read
    And the hub is still serving afterwards

  Scenario: a corrupt catalogue is not described as still being worked out
    Given a catalogue file that is malformed
    When the folder route is asked for a folder
    Then the answer says the catalogue could not be read
    And it does not invite the owner to try again in a minute

  Scenario: the narrow catch stays narrow
    Given a missing rollup table
    When a folder is asked for
    Then the answer is still that the rollup is being worked out
```

## Out of scope

Repairing a corrupt catalogue, or re-cataloguing on a lock. The `files` column malformation the
verifier noted, where one surface serves a row without it and another throws — same family, and it
belongs here only if it costs nothing. Raising `BUSY_MS`, which trades one freeze for another.
