# N7 — live satellite discovery (`estate_register.mjs` + register route)

## Goal

Make "just start prime-silo on the ASUS and it detects" literal: a satellite starting on the same LAN
**registers** with the driver node (T480) — a heartbeat + a session-fingerprint manifest (content-hashes +
quarantine flags only, never payload) pushed to a hub register endpoint — so the hub records last-seen +
reachability and recomputes the N4 drift **live**, without a manual ingest. LAN/loopback-only, authenticated
by a shared per-estate key (reuses the benny keystore). Completes KR2.4: the cockpit reflects the estate as
it actually is, the moment a machine comes online.

## Context pointers (never inline content)

- Plan: `architecture/SOLUTION-estate.md` §8.4 (transport), §10 (privacy on the wire, LAN-auth, additive).
- Reuse: `estate_drift.mjs` (N4 — recompute on register), `bus.mjs` (B1 — publish reachability),
  `estate_api.mjs` (N2/N3 additive `tryHandle` route pattern), the benny keystore key resolution in
  `packaging/desktop/home_resolver.js` / `estate_api.mjs` for the shared secret.
- Privacy R31: the manifest carries content-hashes + quarantine flags, never a session's text.

## TDD plan

1. Failing test: `buildManifest(sessions, quarantine)` emits content-hashes + quarantine flags and NO payload → implement.
2. Failing test: `register(hubState, manifest, auth)` with a bad/absent key is rejected (401-equivalent), state unchanged.
3. Failing test: a valid register updates last-seen + reachability and recomputes drift (delegates to N4).
4. Failing test: a manifest is loopback/LAN-only — a non-local origin is refused.
5. Failing test (mutation/RED): a manifest carrying session content (not just a hash) is rejected by the schema/gate.

## Acceptance (BDD — every Scenario must map to an automated test)

```gherkin
Feature: live satellite registration
  Scenario: a satellite coming online updates drift live
    Given the hub with no recent satellite heartbeat
    When the satellite POSTs a valid signed fingerprint manifest to the register route
    Then last-seen updates, reachability flips to live, and drift is recomputed from the new hashes

  Scenario: unauthenticated or non-LAN registration is refused
    Given a manifest with a wrong shared key or a non-loopback/non-LAN origin
    When it hits the register route
    Then it is rejected and the hub state is unchanged

  Scenario: only hashes cross the wire (R31)
    Given a manifest under construction
    When buildManifest runs
    Then it contains content-hashes and quarantine flags only, never session text (gate RED if payload leaks)

  Scenario: additive route, default unchanged
    Given the existing estate API
    When POST /api/estate/register is added
    Then every prior estate route responds exactly as before
```

## Out of scope

No cloud/WAN transport (LAN/loopback only). No auto-sync on register — drift updates live but a sync still
needs the N5 human-signed approval. No new key infrastructure (reuse the benny keystore). No console redesign
(additive live-reachability badge only).
