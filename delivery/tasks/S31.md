# S31 — opening the top of a drive never scans it on the hub's thread

**The second walk-through stop on the folder view**, found on the real F: on 2026-11-14 within an
hour of S30 merging. The signed path (`delivery/PATH-data-mapping.md`) puts a walk-through stop
ahead of the queue. Band S, 300 lines, declared up front.

## Goal

The owner opens the top of F: in the Library tab and sees its folders and files in under a second,
and the app keeps answering everything else while it does.

## Why (measured on the real T480, 2026-11-14)

Opening the top folder of F: took **12 to 49 seconds**, all of it on the hub's one request thread,
so the whole app stopped answering until it finished — and the panel asking again kept it stopped.
The files that sit directly in a drive's top folder are found through a partial index,
`files_root`, which S26 added. That index is created only when a catalogue pass writes the
catalogue. F:'s last pass finished on 2026-10-25, the day before S26 merged, so F: has no
`files_root`, and S26's stated fallback — sort every file on the drive by size and keep the ones at
the top — walks all 1,117,007 rows of a USB disk: `SCAN files USING INDEX sqlite_autoindex_files_1`,
11.9 s for 4 rows. S26 measured that fallback at 226 ms over 500,000 rows on a temp folder. It was
never run on F: until S30 made the folder figures reachable today.

This is the same defect class as S30: a catalogue older than a feature never gets the feature's
setup. S30 fixed it for the rollup; this fixes it for the index.

## Context pointers (never inline content)

- `server/coordination/lib/library.mjs`: the schema block that creates `files_root`; `SQL.rootFiles`,
  `SQL.childFilesFor`, `SQL.hasRootIndex`; `folderView`; the summary worker; `current()` and the
  `notYet` sentence S30 added.

## What to close

1. **The worker that builds the folder figures also builds the index they rely on**, with the same
   statement the schema uses, so the index is spelled once. A catalogue whose rollup is already
   current gets the index without the rollup being rebuilt.
2. **A missing index starts that worker**, exactly as a missing rollup does since S30.
3. **The drive root is never scanned on the hub's thread.** Without the index, the root folder
   answers that its figures are still being worked out — the S30 sentence — rather than scanning.
   Folders below the root keep their primary-key range and are unchanged.

## TDD plan

Each item gets a test that fails first, built from the state the real F: is in: a finished pass,
a current summary and rollup, and no `files_root`.

## Acceptance

```gherkin
Feature: the top of a drive answers without walking the drive
  Scenario: a catalogue with no root index gets one, without a new pass
    Given a catalogue whose rollup is current and which has no files_root index
    When the owner opens the top folder of that drive
    Then the index is built off the hub's thread
    And no new pass is started and the rollup is not rebuilt

  Scenario: the top folder is never answered by a scan
    Given a catalogue with no files_root index
    When the top folder is asked for
    Then the answer says its figures are being worked out
    And no query on the hub's thread reads every file

  Scenario: the index has one spelling
    Given the schema and the worker both create files_root
    When either creates it
    Then both use the same statement
```

## Pre-registered criteria (real T480, real F:, author's smoke and verifier's judgement)

- After the index exists, the top folder of F: answers in under 1 second, warm.
- While the index is built, the hub answers other requests throughout, as S30's criterion required.
- The time to build the index on F: is reported, whatever it is.

## Out of scope

The speed of the child-folder query at the root (0.86 s on F:, measured, reported, not changed here).
The rollup's own speed. A locked or corrupt catalogue (S29).

## Handoff

Nothing for the owner to do. Until it merges, avoid opening the Library tab's folder view on F:.
