# N0 — estate model + delta sync engine

## Goal

A content-addressed **estate projection** (`estate.mjs` → rebuildable `estate.jsonl`) folding machines,
drive fingerprint manifests, backup snapshots and a content-hash session inventory, plus a **sync engine**
(`estate_sync.mjs`) that dedupes overlapping sources by content (reusing L1 CAS), processes only the delta
(reusing L4 cursors), and emits KEL `sync_*` events. Makes the D: portable copy and the F: backup dedupe to
one blob per unique content and cascade F→D→eGPU delta-only — the substrate the console (N2) renders. Traces
O2.KR2.2 (telemetry/lineage extended to the physical estate) and O1.KR1.5 (corpus coherence for training).

  (L0 appendKelEvent/readKelEvents/foldProjection), `server/coordination/lib/durability.mjs` (L3 doctrine).
- Fingerprint prior art: the F:/D: manifest shape (SHA256 of sorted `relpath|size|mtime` + count + bytes).

## TDD plan

1. `estate.jsonl` folds a fixture (2 machines, 2 drives, N sessions incl. a duplicate across drives) → the
   duplicate session appears as ONE content-hash entry referenced by both drives (dedup). Write first, watch fail.
2. `syncSource` run twice on an unchanged source emits zero new blobs and zero new `sync_*` KEL events beyond
   the first (idempotent / delta-only).
3. A changed session content_hash reprocesses (new blob + one new cursor advance); unchanged ones are skipped.
4. Rebuild identity: fold → delete `estate.jsonl` → rebuild from the same log is byte-identical (L0/L5 doctrine).
5. Mutation (red-first for infra): break the dedup key (key on sid not content) → gate RED; revert → GREEN.

## Acceptance (BDD — every Scenario must map to an automated test)

```gherkin
Feature: content-addressed estate sync
  Scenario: overlap dedupes by content
    Given the same session file present on both the D: portable copy and the F: backup
    When the estate model folds both drive manifests
    Then the session is one content-hash entry referenced by both drives, not two

  Scenario: delta-only re-sync
    Given a source already synced
    When syncSource runs again with nothing changed
    Then no new blob is stored and no new sync KEL event is emitted

  Scenario: changed content reprocesses
    Given a session whose content_hash changed
    When syncSource runs
    Then exactly that session is re-stored and one cursor advance is recorded

  Scenario: the projection rebuilds from the log
    Given an estate.jsonl folded from the KEL
    When it is deleted and refolded from the same events
    Then the rebuilt estate.jsonl is byte-identical
```
