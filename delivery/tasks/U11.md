# U11 — a drive's comings and goings reach the ledger, and an unplugged drive keeps its date

**Scope signed by the owner 2026-11-14** as decision D2 of `delivery/PATH-data-mapping.md`, where
it is called U0a. Band S, 300 lines, declared up front.

## Goal

U0 merged without two things, each because the file it needed was not on U0's allowlist. Both
matter the first time the owner plugs a backup drive in and takes it out again.

## Context pointers (never inline content)

- `server/jobs/drive_watch.js`: appends `driveEvent(...)` and throws when the ledger refuses it.
- `server/coordination/schema/kel-event.schema.json`: the `type` enum. `drive_attached` and
  `drive_detached` are not in it, so every such event is refused today.
- `server/coordination/lib/drive_registry.mjs`: `driveEvent` (payload keys exactly `scope`,
  `identity`, `root`, `medium`), and the comment above `readRegistry` stating the limit below.
- `server/coordination/lib/library.mjs`: `libraryPath(dir, root)` is the only exported spelling of
  a catalogue's file name, and it needs a root.
- `server/coordination/lib/estate_api.mjs`: the `catalogue` callback of `GET /api/estate/drives`
  answers `unknown` for every drive that is not attached.

## What to close

1. **The two event types join the schema.** Nothing else about the events changes; the payload
   never carries a label or a name.
2. **A catalogue is found by identity.** `library.mjs` exports the lookup, and `libraryPath`
   becomes a caller of it, so the file name is still spelled in exactly one place.
3. **An unplugged drive reads one of three things, never a fourth.** A date when its catalogue
   finished; "never catalogued" when the store is there and holds none; "cannot tell" when the
   store itself is not attached. F: holds the store on the T480, so an unplugged F: is the third.

## TDD plan

Each item gets a test that fails first. For 1, an attach and a detach are appended through the
real `appendKelEvents` and read back. For 2, both spellings are asked for one drive and must give
one path. For 3, the Drives tab is rendered and read as a person reads it, once per state.

## Acceptance

```gherkin
Feature: drives leave a record, and an absent drive is still described
  Scenario: plugging a drive in and taking it out are both on the ledger
    Given a drive the registry has not seen
    When it is attached and then detached
    Then the ledger holds one drive_attached and one drive_detached event for its identity
    And neither event carries the drive's label

  Scenario: an unplugged drive that was catalogued still says when
    Given a catalogued drive that is no longer attached
    When the owner opens the Drives tab
    Then its row shows the date its catalogue finished

  Scenario: an unplugged drive that was never catalogued says so
    Given a drive seen once and never catalogued, no longer attached
    When the owner opens the Drives tab
    Then its row says never catalogued, and shows no date

  Scenario: when the store is unplugged the tab cannot tell, and says that
    Given the drive holding the estate store is not attached
    When the owner opens the Drives tab
    Then no drive is said to be never catalogued

  Scenario: a catalogue's file name has one spelling
    Given one drive known by both its root and its identity
    When its catalogue is asked for each way
    Then both answers are the same file
```

## Out of scope

Catalogue dates for drives on another machine (U2–U5, deferred by D4). Starting a catalogue from
the Drives tab (U1). Stylesheet rules for the Drives tab.

## Handoff

Nothing for the owner to do. After merge, plugging in a backup drive leaves an event, and taking it
out leaves its row with a date.
