# U0 — the drive registry: every drive by what it is, and when it was last seen

## Goal

The owner opens the Estate Map's **Drives** tab and sees every drive this machine has ever had
attached:
- internal disks, F:, and each backup drive;
- by identity, never by letter;
- each drive's label, medium (internal, USB, network), capacity and free space, and whether it is
  attached now;
- when each was first and last seen, and when its catalogue last finished.

On the Windows system drive it also shows **where the owner's data is**: Downloads, Documents,
Desktop, Pictures, Videos, Music and OneDrive, wherever each has been redirected. Those folders,
not the whole drive, are what the estate catalogues there (owner direction, 2026-10-11).

Plugging a drive in, or taking it out, is noticed and recorded. A backup drive plugged in at a
different letter next month is the same row. This is the foundation EP-U builds on: copies count
only on drives the estate knows and has seen recently (SOLUTION-consolidation §2, invariants 4–5).
It reads volume metadata and the user's folder locations only, never a file. This machine only;
other machines' drives arrive through the replicated ledger (U2–U4).

## Why user folders, not whole drives (owner direction and measurement, 2026-10-11)

The owner: "when looking at the windows machine only look for where the user data is; do not carry
the overhead of the operating system; the downloads folder is a very good place to start".

Measured on the T480's C: from Everything's index (totals only):

## Design

1. **One identity function, per platform.**
   - On Windows the identity stays exactly S21's: volume serial plus root file ID. A test proves the
     value is unchanged, so no existing catalogue changes name.
   - On Linux, the device number S21 uses changes across reboots and USB ports. Identity there is the
     filesystem UUID (`lsblk -J -o UUID,…`), prefixed `uuid:`.
   - `rootIdentity` delegates to the new `driveIdentity` on Linux only.
2. **Volume facts from the operating system.**
   - **Windows:** one PowerShell call through S2's `capture()`: `Get-Volume` joined to
     `Get-Partition` and `Get-Disk`, giving drive letter, file-system label, file system, drive type,
     size, remaining space and the disk's bus type (USB, SATA, NVMe, …).
   - **Linux:** `lsblk -J` (UUID, label, fstype, size, available space, mount point, transport,
     hotplug).
   - **Medium** is `usb` for the USB bus or transport, `internal` for SATA, NVMe or SCSI, and
     `network` for mapped network drives. A network drive is recorded but marked "catalogued by
     its own host": its files are fingerprinted on the machine that owns the disk (invariant 1).
   - Capacity and free space use `fs.statfs` where the OS call omits them.
3. **The registry lives on the machine, not on a removable drive.** It is SQLite at
   `BENNY_HOME/estate/drives.db`; F: comes and goes, so the registry cannot live there. It has one
   row per identity:
   - label, owner name, file system and medium;
   - capacity, free space and the root last seen at;
   - first and last seen, attached;
   - `retired_at`, reserved for U9 and always null in U0.
4. **Watching.** `server/jobs/drive_watch.js` is an interval job (default 60 s,
   `ESTATE_DRIVE_WATCH_SECONDS`) that compares what is attached with the registry.
   - A new identity is added.
   - A known identity reappearing, at any letter, is the same row and `drive_attached` is logged.
   - A disappearance logs `drive_detached`.
   - Each event goes once into the estate's KEL log, carrying identity, machine, root and medium.
   - A drive whose identity cannot be read (an unreadable root) is reported as "attached, identity
     unknown" and never merged with another row.
5. **Labels and privacy.**
   - A volume label is the owner's own text, so it is judged with `volumeNameProblem` against the
     quarantine rules, and a label a rule matches is shown and logged as "label withheld".
   - The owner may set a display name for any drive with `PATCH /api/estate/drives/:id` (loopback
     only). It is stored beside the volume label, never written to the drive, and judged by the
     same rules.
6. **Fresh or stale.** `ESTATE_COPY_FRESH_DAYS` (default 30) is added to `commands/params.yaml`.
   A drive last seen longer ago is "stale". U6 uses the same parameter, and in U0 it only labels
   the row.
7. **Where the user's data is (Windows).**
   - The registry marks the **system drive**, the one holding `%SystemRoot%`.
   - It resolves the user's known folders from the registry key
     `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders`, with
     variables expanded. That key follows redirection to OneDrive or another drive, which a guessed
     `C:\Users\<name>\Downloads` would not.
   - **Downloads is first**, then Documents, Desktop, Pictures, Videos and Music, plus the OneDrive
     root from `%OneDrive%`.
   - Each user root is recorded against the drive it actually sits on, with its identity
     (`driveIdentity` of the folder), its role (`downloads`, `documents`, …), and whether it is in
     OneDrive.
   - A system drive is never offered for cataloguing whole. Its **user roots** are what U1 and the
     Library offer.
   - A drive without Windows (F:, backup drives) is a **data drive** and is offered whole, subject
     to S23's scope rules.
   - Other folders in the profile are listed as "other profile folders: not catalogued unless you
     add them". The owner may add one as a user root through `PATCH /api/estate/drives/:id`
     (loopback only, recorded).
   - `C:\Windows`, Program Files, ProgramData and AppData are never user roots and cannot be added.
   - On Linux (the Pi), the user root is `$HOME`, plus any mounted data drive.
8. **Catalogue column.** Each row shows its catalogue's last finished pass, read with S21's
   `libraryPath` and pass record ("never catalogued" if there is none). Nothing is started from
   here.
9. **API and panel.**
   - `GET /api/estate/drives` (loopback only, like the library) returns the registry with
     attached, stale and catalogue state.
   - The Estate Map gains a **Drives** tab with one row per drive: name or label, medium, capacity
     and free space, attached now (at which letter), first and last seen, stale, and catalogue
     status.
   - Under the system drive, it lists its user roots: Downloads first, each with its role and
     whether it is in OneDrive, and its file count and size from Everything's index when available.
     Those are metadata only.
   - It reports what the OS calls returned, never a guess: a field the OS did not give is shown as
     "unknown".

## TDD plan

1. `drive_registry_test`, with fake PowerShell and lsblk outputs captured from real shapes:
   - **Parsing:** volumes parse with the correct medium (USB vs internal vs network).
   - **Identity:** on Windows it equals S21's `rootIdentity` for the same root. On Linux it is the
     UUID, stable when the device number changes.
   - **Registry:** a new drive is added; the same identity at another letter is the same row with
     one `drive_attached`; removal gives one `drive_detached`; a repeated tick with nothing changed
     writes no events.
   - **User roots:** a fake User Shell Folders answer, with Downloads on C:, Documents redirected
     to OneDrive and Pictures on D:, maps each root to its real drive and role, Downloads first. The
     system drive is offered only through its user roots. A data drive is offered whole. Adding
     `C:\Windows`, Program Files, ProgramData or AppData as a user root is refused.
   - **Edge cases:** an unreadable identity is never merged; a label matching a quarantine rule is
     withheld in the API, panel and KEL; an owner name is judged the same way; stale follows
     `ESTATE_COPY_FRESH_DAYS`.
2. Routes: loopback only (403 otherwise); PATCH sets only the owner name; 400 for an unknown
   identity.
3. Job: disabled without `BENNY_HOME`; runs on the primary only under its named lock; one tick per
   interval.
4. `estate_compare_test`: `rootIdentity` on Windows is byte-identical to its S21 value.
5. Panel: the Drives tab renders attached, stale, retired-reserved and never-catalogued rows
   through the real view.
6. Gate `u0.mjs`: the U0 tests, then the S21 gate (shared estate API, panel and identity).

## Pre-registered criteria (real T480, verifier, reported either way)

- Every volume Windows reports (`Get-Volume` with a drive letter) appears, with F: as `usb` and C:
  as `internal`. Capacity and free space are within 1% of Windows' own figures.
- A real drive unplugged and plugged back in (owner's action, or a VHD the verifier attaches and
  detaches) gives exactly one detached and one attached event within two ticks, and the same row.
- An idle hub's watch job costs ≤ 2 s of CPU per hour.
- The T480's user roots match Explorer's own: Downloads on C:; Documents, Desktop and Pictures in
  OneDrive. Their file counts and sizes are within 1% of Everything's (Downloads: 779 files,
  40.1 GB on 2026-10-11).

## Out of scope

- Other machines' drives (they arrive through the ledger, U2–U4); the Pi live (fixtures cover its parsing, and the live Pi
  comes with U1).
- OneDrive as a registry row (counted as a cloud copy in U6).
- Starting catalogues from the Drives tab (the Library tab does that); retiring drives (U9).

## Handoff

One gate run and one independent check by a non-author verifier on the real T480. The verifier:
- compares the registry with `Get-Volume`;
- attaches and detaches a test VHD (or asks the owner to replug a USB drive) and confirms the
  events and the same row at a new letter;
- confirms S21's catalogue names are unchanged.
