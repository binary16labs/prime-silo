# S30 — a catalogue summarised before the folder weights existed still gets them

**The first stop of the M13 walk-through**, found on the real F: on 2026-11-14 before the owner
sat down. The signed path (`delivery/PATH-data-mapping.md`) makes a walk-through stop the next
contract, ahead of phase 2. Band S, 300 lines, declared up front.

## Goal

The owner opens a folder of F: and sees its weight. Today the hub answers "F:'s folder rollup is
still being worked out: try again in a minute" and it will say that for ever.

## Why (measured on the real T480, 2026-11-14)

F:'s catalogue finished its pass on 2026-10-25 and its summary was saved then. S26 merged the day
after. The worker that builds the rollup is started from one place, and only when the saved
summary's key differs from the current one. On F: the two are equal, so no worker starts: nine
minutes after the hub came up the `folders` table held 0 rows, against the 157 s the build takes.
Every catalogue summarised before S26, under rules that have not changed since, is in this state.
The folder route is a consumer whose producer never runs.

## Context pointers (never inline content)

- `server/coordination/lib/library.mjs`: `workOut`, its single caller in `current()`, `rollupKey`,
  and the worker block that runs `buildFolderRollup` then `markRollup`.
- `tests/library_test.mjs`: S26's rollup tests, which all begin from a fresh pass.

## What to close

1. **A current summary with a missing or stale rollup starts the worker.** The rollup's own key
   is checked wherever the summary's is, so either being behind is enough.
2. **Nothing is recomputed that is already right.** A catalogue whose summary and rollup are both
   current starts no worker.
3. **"Try again in a minute" is only said while something is working.** If nothing is, the answer
   names that instead.

## TDD plan

Each item gets a test that fails first, and the first is built from the state the real F: is in:
a finished pass, a saved summary under the current key, and no rollup.

## Acceptance

```gherkin
Feature: folder weights reach catalogues that predate them
  Scenario: a catalogue with a current summary and no rollup gets one
    Given a catalogue whose summary is current and whose folder rollup was never built
    When the owner opens a folder of that drive
    Then the rollup is built without a new pass
    And the folder's weight is shown once it is

  Scenario: a catalogue that is fully current is left alone
    Given a catalogue whose summary and rollup are both current
    When the owner opens a folder of that drive
    Then no worker is started

  Scenario: waiting is only promised while work is under way
    Given a rollup that is missing and no worker running for it
    When the folder route answers
    Then it does not say to try again in a minute
```

## Pre-registered criteria (real T480, verifier, reported either way)

- On the real F: catalogue, with no new pass: the root folder answers 200 within 10 minutes of the
  hub starting, and the `folders` table is non-empty.
- The hub serves other requests throughout the build.

## Out of scope

The rollup's own speed. The 1,500-file cap (D10). A locked or corrupt catalogue (S29).

## Handoff

Nothing for the owner to do. Until it merges, pressing Catalogue on F: starts a new pass, and the
rollup is built at the end of that.
