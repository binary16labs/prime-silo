# U8 — the signed copy: read back, never overwriting, never touching the source

**AUTHORED 2026-11-18, AWAITING THE OWNER'S SIGNATURE.** This is the first contract that writes
the owner's data. It is stage 3b of `delivery/PLAN-consolidate-first.md` (signed: F: is the one
drive, the T480 its only writer, everything before the backup only adds). It re-scopes S7, and
uses robocopy as `PATH-data-mapping.md` D12 says.

## Goal

A U7 proposal **the owner signed** is carried out exactly as shown. Each file is copied to its
planned place on F: and read back against its sha256 before it counts. The source is never
changed, and F: is never overwritten. The first real run is Downloads: 774 files, 30 GB.

## Design

1. **Only a signed, current proposal runs.** Every refusal names its reason. A run needs:
   - `isAuthorised` to hold (a human signature);
   - U7's planner, asked now, to give the same `proposal_id`;
   - the item list to re-hash to the proposal's `digest:`;
   - the drive at the target letter to have the identity of the F: catalogue the plan was made
     against;
   - this hub to be the T480's, with no pass on F: and no other copy running;
   - free space now to be at least the bytes plus 10 GB. This closes U7's note: the fit is checked
     at run time.
2. **Staging, then checking, then placing.** Items run in batches, one source folder each:
   1. The source folder is probed with `windowsCloudOnly`. A file that is cloud-only now is
      skipped and counted, never opened, since robocopy would download it.
   2. robocopy copies the batch into `F:\consolidated\.staging\<proposal_id>\` with
      `/COPY:DAT /DCOPY:T /Z`. It never runs with `/MOV`, `/MIR` or `/PURGE`, and a test asserts
      this.
   3. Each staged file is read back. If its sha256 matches, it is placed by a **hard link to its
      final name**. A link fails on an existing name, so nothing is overwritten, even in a race.
      If it does not match, the source has changed: the file is skipped and counted. Either way
      its staging entry is removed.
3. **A run can be resumed and stopped.** On a re-run:
   - a file already in place with the right sha256 counts as "already there";
   - a name that holds other content is refused.

   The run happens in a worker, not on the hub's thread. The panel shows "Step n of m", the files
   and GB done, and a Stop button.
4. **Repeats** (`same_as`) are not copied. They are recorded as pointers to the one copy.
5. **The ledger.** One `proposal_executed` event carries the `run_id`, the `proposal_id` and
   counts only, never paths. This gives `unauthorisedRuns` its first real population, so the
   SS1/23 gauge reads "0 of N" instead of "0 of 0". The per-file record goes to
   `<store>/library/copies/<run_id>.jsonl`. Private paths are counted, never named.

## TDD plan

Temp folders and a temp governance log are used throughout; the signature is made only in that
temp log.

1. One refusal test for each condition in design 1, plus a run whose signature was made by an
   agent.
2. Placed files have the planned sha256 and the source's modified date. Staging is empty at the
   end. robocopy's arguments are asserted.
3. A name created after the plan is refused and keeps its bytes.
4. A changed source file is skipped. A cloud-only file is never opened (the probe is stubbed, as in
   U12).
5. A worker killed mid-run and run again ends in the same state as a run that was not killed.
6. A metadata snapshot of the source (paths, sizes, modified dates) is identical before and after.
7. There is one `proposal_executed` event, with no paths. `unauthorisedRuns` flags a run that has
   no signature.
8. Panel: Copy appears only on a signed proposal; otherwise the reason shows. Progress and Stop
   work.
9. Gate `u8.mjs`: the U8 tests, then the U7 gate.
