# W4 — Harden the enforcement W2 shipped

## Goal

W2 made the allowlist machinery, but `claude-w2-verifier` **defeated its purity check on a live
test** and the author found a second defect while dogfooding. Close both. This is not polish: a
guarantee that can be evaded is worse than no guarantee, because the board now trusts it.

## Context pointers

- LOG 2026-08-03 `W2 | note | claude-w2-verifier` — the exact evasion, reproduced by the verifier
- LOG 2026-08-03 `W2 | note | claude-opus` — DEP0190 found while dogfooding P0
- `server/coordination/lib/sandbox_provision.mjs` — the `=== IMPURE BELOW THIS LINE ===` marker
- `server/coordination/lib/work_loop.mjs` — `workVerify`'s spawn

## The two defects, precisely

1. **The purity check is regex text-matching over the slice, comments included.** It catches a
   literal `spawnSync(` / `fs.x(` and nothing else. The verifier got impure code above the marker
   using a dynamic import aliased through an object and reached by property access — no literal call
   syntax — and the gate still exited 0. `process.env` reads and `new Date()` are not checked at all.
   Its first attempt tripped the check only because an explanatory **comment** contained the string
   `spawnSync(`, which is itself the proof that the check reads text rather than code.
2. **`DEFAULTS.worktreeRoot` reads `process.env` above the marker**, so the marker's own stated claim
   — "everything above is a pure function of injected inputs" — **is false as written**. Harmless
   today (the three exported checks never reference `DEFAULTS`) but the claim must become true or be
   narrowed to what is actually enforced.
3. **`workVerify` spawns with `shell: true` and an args array** (DEP0190): arguments are concatenated
   unescaped. The command comes from w0-validated, board-signed frontmatter so exposure is small —
   but "small" is not the standard this gate is held to.

## TDD plan

1. Red: reproduce the verifier's exact evasion as a fixture — an aliased dynamic import reached by
   property access above the marker — and assert the check REJECTS it.
2. Red: a `process.env` read and a `new Date()` above the marker are both rejected.
3. Red: a comment containing `spawnSync(` does NOT trip the check (no false positives — the current
   check fails this).
4. Implement: parse rather than grep, or move to a declarative export boundary that cannot be
   evaded by aliasing. 5. Move `DEFAULTS` below the marker (or narrow the claim). 6. Replace the
   shell spawn so args are never concatenated.

## Acceptance

```gherkin
Feature: the purity guarantee cannot be evaded
  Scenario: an aliased impure call above the marker is caught
    Given a module reaching child_process through an alias and property access above the marker
    When the purity check runs
    Then it rejects the module naming the offending construct

  Scenario: comments are not code
    Given a comment above the marker containing the text "spawnSync("
    When the purity check runs
    Then it does not fail — a false positive is as much a defect as a false negative

  Scenario: the marker's claim is true
    Given the region above the marker
    When it is analysed
    Then nothing there reads process.env, the clock, the filesystem, or a process

  Scenario: verify commands are not shell-concatenated
    Given a contract whose verify command contains shell metacharacters
    When work verify runs it
    Then the arguments are passed without shell concatenation
```
